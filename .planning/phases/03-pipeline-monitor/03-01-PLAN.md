    基于 Task 1 的分析结果，进行用户优化点调研和需求设计。产出 3-5 个具体可执行的优化需求，每个需求包含：

    1. **需求背景**: 当前的问题或用户痛点（引用 Task 1 中的发现）
    2. **优化目标**: 预期的用户体验改善
    3. **设计方案**: 具体的技术实现方案，包括：
       - 需要修改的文件
       - 核心变更逻辑
       - 前后端数据流变化
       - 兼容性考虑（不影响现有功能）
    4. **验收标准**: 可验证的完成条件

    需求候选方向（基于代码分析，但不限于此）：

    **需求 A: 消除 SSE 事件双路径处理歧义**
    - 背景: 分析发现 `useSSE.ts` 的命名事件监听器与 `onMessage` 回调可能同时处理 `pipeline_update` 事件（取决于 `sse_broadcaster.py` 的发送格式）
    - 设计: 统一 SSE 事件处理架构——要么全部使用命名事件（`addEventListener`），要么全部使用无名事件（`onmessage` + `data.type` 判断），消除歧义
    - 影响: useSSE.ts 的 `storeHandlers` 与 `onMessage` 协作逻辑，sse_broadcaster.py 的 `event_stream` 格式

    **需求 B: loadAll() 增加 run history 加载 + 一致性保证**
    - 背景: `loadAll()` 不调用 `fetchRuns()`，历史运行记录页面在 `loadAll` 后不刷新
    - 设计: 在 `loadAll()` 中添加 `pipeline.fetchRuns()` 调用。同时统一所有操作后调用 `loadAll()` 而非零散的手动刷新
    - 影响: usePipelineMonitor.ts 的 `loadAll()`，PipelineMonitor.vue 的 `handleTriggerWithVerify`、`handleCancelWithVerify` 等

    **需求 C: KPI 卡片数据口径澄清**
    - 背景: "自动爬虫"卡片的 sub 文案中 `pipeline.dataSources.length + active_data_sources` 可能重复计数
    - 设计: 明确区分自动数据源和手动数据源的口径，修改 sub 文案为 `{auto_count}个自动 + {manual_count}个手动`，从 API 获取 manual 数据源计数或从 dataSources 中按类型过滤
    - 影响: usePipelineMonitor.ts 的 `kpiCards` computed，可能需要后端返回手动数据源计数

    **需求 D: 操作后数据一致性刷新**
    - 背景: `handleTriggerWithVerify` 不调用 `loadAll()`，导致触发后数据质量/数据源面板可能显示旧数据。而 `handleCancelWithVerify` 调用了 `loadAll()`，存在不一致
    - 设计: 抽取 `verifyState` 中的 `loadAll()` 调用为统一模式——所有操作（trigger/cancel/retry/resume）后都调用 `loadAll()` 刷新全页面
    - 影响: PipelineMonitor.vue 的 `handleTriggerWithVerify`、`handleCancelWithVerify`、`handleRetryStage` 等

    **需求 E: 阶段依赖配置后端化**
    - 背景: `_DEPS` 硬编码在 usePipelineMonitor.ts 中，与后端 executor.py 的 DAG 定义可能不一致
    - 设计: 新增 API 端点 `GET /pipeline/stage-deps` 返回阶段依赖关系图，前端消费此数据替换硬编码 `_DEPS`
    - 影响: backend/routes.py 新增端点，usePipelineMonitor.ts 移除 `_DEPS`，改为 API 调用

    每个需求必须包含可行性评估（基于现有代码架构，指出实现复杂度）。

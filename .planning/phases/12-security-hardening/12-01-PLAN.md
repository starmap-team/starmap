# Phase 12-01: PyJWT + bcrypt + JWT Claims Hardening

**Phase:** 12 — 安全加固
**Wave:** 1
**Requirements:** SEC-01, SEC-02, SEC-03
**Depends on:** none

## Goal

Replace the hand-written HMAC+base64 JWT implementation with PyJWT, replace plaintext password comparison with bcrypt.checkpw() (dual-format parsing for transition), and add aud/iss/nbf/jti claims to new tokens with two-phase enforcement. This wave has no external dependencies and all three SEC items can be implemented in parallel within the same commit or as sequential atomic commits.

   ```python
       """签发 JWT（PyJWT），与 dependencies.py _decode_token 验证逻辑一致。"""
   ```

### Task 3: Replace hand-written JWT decode with PyJWT (SEC-01)
**Type:** code
**Files:**
- `backend/app/dependencies.py` — replace `_decode_token` implementation, update imports

**Details:**
1. Remove the inline imports inside `_decode_token`: `import base64`, `import hashlib`, `import hmac`, `import json`, `import time`
2. Add top-level import: `import jwt`
3. Replace `_decode_token` body (lines 52-88) with:
   ```python
   def _decode_token(token: str) -> dict[str, Any]:
       """解码 JWT token。使用 PyJWT，密钥来自 settings.secret_key。"""
       try:
           payload = jwt.decode(
               token,
               settings.secret_key,
               algorithms=["HS256"],
               options={
                   "require": ["exp", "iat", "sub"],
                   "leeway": settings.jwt_leeway_seconds,
               },
           )
       except jwt.ExpiredSignatureError as e:
           raise ValueError("JWT expired") from e
       except jwt.InvalidTokenError as e:
           raise ValueError(f"Invalid JWT: {e}") from e
       return payload
   ```
4. **Critical:** Preserve `ValueError` as the raised exception type. The existing `get_current_user` and `get_current_user_sse` handlers catch `ValueError` and map it to `AuditEvent.TOKEN_EXPIRED` (if "expired" in message) or `AuditEvent.TOKEN_INVALID`. The new code must raise `ValueError("JWT expired")` for expired tokens and `ValueError(f"Invalid JWT: ...")` for all other failures.
5. Phase A: Only require `["exp", "iat", "sub"]` — the existing claims. New claims (aud/iss/nbf) are added to issuance in Task 4 but not yet required on decode. This ensures old tokens without the new claims still work during the transition window.

**Verification:**
- Token issued by old hand-rolled code decodes successfully via new `_decode_token`
- Token issued by new PyJWT `_encode_jwt` decodes successfully
- Expired token raises `ValueError("JWT expired")`
- Tampered token raises `ValueError("Invalid JWT: ...")`
- `get_current_user` still maps ValueError to correct audit events

**In `auth.py`**, extend the payload dict in the `login` handler (currently lines 72-78):

```python
payload: dict[str, str | int | float] = {
    "sub": matched["username"],
    "role": matched["role"],
    "username": matched["username"],
```

### Task 5: Replace plaintext password comparison with bcrypt (SEC-02)
**Type:** code
**Files:**
- `backend/app/api/v1/auth.py` — add `_verify_password` function, modify `login` handler
- `backend/app/config.py` — add production plaintext password rejection in model_validator

**Details:**

**In `auth.py`**, add a new helper function after `_encode_jwt`:
```python
def _verify_password(plain: str, stored: str) -> bool:
    """验证密码。支持 bcrypt hash 和明文（过渡期）。

    bcrypt hash 以 $2b$ 或 $2a$ 开头，否则视为明文。
    """
    if stored.startswith(("$2b$", "$2a$")):
        return bcrypt.checkpw(plain.encode(), stored.encode())
    # Legacy plaintext fallback (transition period)
    return plain == stored
```

Add `import bcrypt` to the top-level imports.

**Modify the `login` handler** — replace the plaintext comparison loop (lines 58-62):
```python
# Before:
for u in users:
    if u["username"] == request.username and u["password"] == request.password:
        matched = u
        break

# After:
for u in users:
    if u["username"] == request.username:
        if _verify_password(request.password, u["password"]):
            matched = u
        break  # Only one entry per username; stop after finding the match
```

**In `config.py`**, add production plaintext password rejection to the `_resolve_postgres_uri_and_warn` model_validator (after the SECRET_KEY length check, around line 183):
```python
# SEC-02: 生产环境禁止明文密码
if self.app_env == "production":
    plaintext_users = [
        u["username"] for u in self.parsed_users
        if not u["password"].startswith(("$2b$", "$2a$"))
    ]
    if plaintext_users:
        raise RuntimeError(
            f"Plaintext passwords not allowed in production for users: {plaintext_users}. "
            f"Use bcrypt hash: python -c \"import bcrypt; print(bcrypt.hashpw(b'YOUR_PW', bcrypt.gensalt()).decode())\""
        )
```

Also add a startup warning for non-production environments (after the production check):
```python
else:

        u["username"] for u in self.parsed_users
        if not u["password"].startswith(("$2b$", "$2a$"))
    ]

            "⚠️  以下用户使用明文密码（建议迁移到 bcrypt hash）：{}",
```

**AUTH_USERS dual-format:** The existing `parsed_users` property (config.py lines 204-218) does NOT need changes. The `username:password_or_hash:role` format already works because bcrypt hashes contain `$` characters (e.g., `$2b$12$...`) which do not conflict with the `:` delimiter. The detection logic is in `_verify_password`, not in parsing.

### Task 6: Add bcrypt hash generation utility
**Type:** code
**Files:**
- `backend/app/utils/hash_password.py` — new file (CLI utility)

**Details:**
Create a small utility script for generating bcrypt hashes from plaintext passwords, to help operators migrate AUTH_USERS entries:
```python
"""Utility: generate bcrypt hash for AUTH_USERS migration.

Usage:
    python -m app.utils.hash_password <plaintext_password>
    # Output: $2b$12$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
"""
import bcrypt
import sys


def hash_password(plain: str) -> str:
    """Generate bcrypt hash for a plaintext password (work factor 12)."""
    return bcrypt.hashpw(plain.encode(), bcrypt.gensalt(rounds=12)).decode()


if __name__ == "__main__":
    if len(sys.argv) != 2:
        print("Usage: python -m app.utils.hash_password <plaintext_password>")
        sys.exit(1)
    print(hash_password(sys.argv[1]))
```

**Verification:**
- `cd backend && poetry run python -m app.utils.hash_password test123` outputs a `$2b$12$...` string
- The output hash can be used in AUTH_USERS and `_verify_password` returns True

## Risk Assessment

| Risk | Severity | Mitigation |
|------|----------|------------|
| Old tokens break after PyJWT migration | Low | PyJWT HS256 output is format-compatible; PyJWT decoder handles both padded and unpadded base64url. Tested in Task 7. |
| Plaintext passwords in production | Critical | Production startup validation rejects plaintext passwords (Task 5). Non-production gets a warning. |
| Clock skew causes token rejection | Medium | `jwt_leeway_seconds=30` (configurable) tolerates 30s clock drift (Task 3). |
| Two-phase claim enforcement gap | Medium | Phase A only requires existing claims; Phase B (after token_expire_hours) enforces new claims. Document the follow-up task. |
| bcrypt hash contains `$` conflicting with AUTH_USERS `:` delimiter | None | bcrypt hashes use `$` as version/salt separators, never `:`. No conflict. |
| `parsed_users` property needs changes | None | No changes needed — the property already splits on `:` and stores the password field as-is. Detection is in `_verify_password`. |

## Success Criteria

1. `auth.py` uses `jwt.encode()` / `jwt.decode()` — no hand-written HMAC+base64 code remains
2. Password comparison uses `bcrypt.checkpw()` for `$2b$`/`$2a$` prefixed hashes, with plaintext fallback for transition
3. New JWT tokens contain `aud="starmap-api"`, `iss="starmap"`, `nbf`, and `jti` claims

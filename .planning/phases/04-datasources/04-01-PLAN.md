    - `summaryStats` computed（第 45-48 行）：`src.filter((s: any) => ...)` / `src.reduce((sum: number, s: any) => ...)` 对已类型化的 `DataSourceDetail[]` 使用 `as any` 回调——类型逃逸，无必要
    - KPI"异常数据源"（第 228 行）：`total - active` 把 `paused`（已暂停）也计为异常，语义上 paused 是人为停用而非异常，应只计 `error` 状态
    - `handleSync`（第 38-44 行）：同步成功/失败仅 ElMessage 一次性提示，触发后依赖 store 内 `fetchSourceDetail` 刷新单个 selectedSource，但卡片列表 `dsStore.sources` 未刷新——同步后卡片上的"最后同步"时间不会更新，闭环断在最后一步

    **第 2 层 — 图表组合式函数 (useDataSourceCharts.ts, 159 行)**
    - `getDailyVolumeOption(volumes: number[])`（第 45-74 行）：x 轴标签用 `WEEKDAY_LABELS`（一二三四五六日，第 43 行）按索引映射——仅当传入恰好 7 个元素且按周一至周日排列时标签才正确；后端 stats 的 `crawl_volume` 是 `{date, count}[]` 按日历日排列（datasource.py 第 304-309 行），直接喂给此函数会标签错位
    - `SOURCE_TYPE_LABELS`（第 90-97 行）：覆盖 crawler/api/manual/import/reference/internal，但后端 `DataSourceCreateRequest.source_type` 允许 `job_board|blog|esco|manual|rss|api`（datasource.py 第 369 行）——job_board/blog/esco/rss 四种类型在卡片上显示原始英文值

    **第 3 层 — Store 与类型 (datasource.ts 162 行 + types/datasource.ts 19 行)**
    - `triggerSync`（datasource.ts 第 117-131 行）：POST `/admin/datasources/${id}/sync`——后端 sync 端点注册在 `router`（prefix `/datasources`，datasource.py 第 328 行），`admin_router` 只有 GET "" 和 POST ""（第 375、391 行），**该 URL 恒 404**，页面上每次"一键同步"必失败
    - `updateSource`（datasource.ts 第 84-100 行）：PUT `/admin/datasources/${id}`——后端 PUT 在 `/datasources/{source_id}`（datasource.py 第 215 行），admin_router 无 PUT 端点，同样 404（本页面未调用，但 DataSourceManager.vue 等其他消费者可能受影响，需 grep 确认调用方）
    - `DataSourceStats` 接口（datasource.ts 第 36-44 行）：定义 `daily_volume/weekly_volume/monthly_volume/avg_daily_count/total_count`，后端 `DataSourceStatsResponse`（datasource.py 第 71-81 行）返回 `crawl_volume/quality_trend/total_runs/successful_runs/failed_runs/avg_records_per_run/source_name`——**字段零重叠**，fetchStats 的消费者读到的全是 undefined
    - `DataSourceDetail.last_crawl_at: string`（types/datasource.ts 第 12 行）：后端可为 `null`（datasource.py 第 41 行），类型应为 `string | null`；`daily_crawl_volume: number[]`（第 17 行）后端从不返回，应为可选或移除
    - `fetchSources`（datasource.ts 第 56-67 行）：`request.get('/datasources') as DataSourceDetail[]`——无响应结构校验（AGENTS.md 约定 Store 中应使用 useResponseValidation，DEV 环境 warn）

    **第 4 层 — 后端 API (datasource.py, 407 行)**
    - `/datasources/health`（第 153-197 行）：循环内查询（第 174-181 行）`select(PipelineRun).where(run_type == "source_sync").order_by(started_at.desc()).limit(1)` **没有按数据源过滤**——`PipelineRun` 模型根本没有 source 外键（pipeline_models.py 第 14-87 行），所有数据源的 `recent_run_status` 返回同一个全局最新运行状态，逐源健康是假象；同时构成 N+1 查询（每个源一次相同查询）
    - `/datasources/{source_id}/stats`（第 255-325 行）：第 276-281 行聚合窗口内**全部** PipelineRun，未按 source_id 过滤（同一根因：PipelineRun 无 source 归属）——任意数据源的 stats 页显示的都是全局统计
    - `POST /{source_id}/sync`（第 328-352 行）：`trigger_and_start(run_type="source_sync")`（executor.py 第 1002-1005 行签名仅接受 run_type + selected_stages）不携带任何源标识，run 创建后与 DataSourceRecord 无关联，也不更新 `last_crawl_at`——"单源同步"实际执行通用管线，响应中的 source_name 仅用于文案
    - `_serialize` 返回 `config=ds.config or {}`（第 129 行）：config 字段模型注释明确含"API密钥、请求频率"（pipeline_models.py 第 194-199 行），而 `GET /datasources` 列表端点**无鉴权依赖**（第 137 行）——任意登录用户可读取全部数据源的配置（含潜在密钥），信息泄露
    - 全部 Pydantic 模型内联在路由文件（第 33-110 行）：违反 AGENTS.md"Schema 集中管理"约定（应在 `backend/app/schemas/`）。评估迁移成本，作为低优先级需求候选
    - PUT 端点的冗余校验（第 232-234 行）：`body.status` 已是 `Literal["active","paused","error"]`（第 53 行），Pydantic 先行强校验后 `if body.status not in (...)` 分支不可达——死代码

    **第 5 层 — 契约与挂载 (openapi.yaml + router.py)**
    - 确认 router.py 第 28-29 行挂载方式：`datasource_router` 与 `datasource_admin_router` 的前缀，核对前端每个 request URL 是否有真实后端路由（重点验证第 3 层的两个 404 结论）
    - 对比 openapi.yaml 中 `/datasources`（第 2893 行）、`/datasources/health`（第 2936 行）、`/datasources/{source_id}/stats`（第 2950 行）、`/datasources/{source_id}/sync`（第 3665 行）的 schema 与 datasource.py 实际响应模型的一致性——契约优先原则要求任何响应结构变更先改此文件

    - 验收: 图表显示的数据与后端返回值一致，无"恒空"字段；或字段从类型与模板中彻底移除

    **需求 C: health / stats 的数据源归属修复**
    - 背景: health 的 recent_run_status 是全局值伪装成逐源值（datasource.py 第 174-181 行，N+1 且无源过滤）；stats 聚合全部 run（第 276-281 行）。根因同为 PipelineRun 无 source 归属
    - 设计方向: ① health 查询提出循环外单次执行，recent_run_status 无法归源时返回 null 并在契约中修正语义（而非继续展示误导值）；② stats 在归属方案落地前明确文档化"当前为全局统计"，或随需求 A 的归属方案一并修复；③ 前端 DataSourceStats 接口与后端 DataSourceStatsResponse 字段对齐（当前零重叠，datasource.ts 第 36-44 行 vs datasource.py 第 71-81 行）
    - 验收: health 接口单次查询、语义诚实；stats 接口前端接口定义与响应逐字段一致

    **需求 D: 配置脱敏与枚举对齐（安全 + 一致性）**
    - 背景: GET /datasources 无鉴权且返回含潜在 API 密钥的 config（datasource.py 第 129、137 行；pipeline_models.py 第 194-199 行）；source_type 枚举前后端不一致（后端 job_board/blog/esco/rss，前端标签表未覆盖）

    - 验收: 非 admin 响应中不含敏感配置键；四种新类型卡片显示中文标签

    - 验收: 异常计数只含 error；无 as any；同步成功后 sources 列表刷新

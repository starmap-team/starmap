> 这是一个标准的全栈分层架构。我重点介绍几个关键设计决策：
>

### 幻灯片 4 | 核心业务流程

**标题**: 四大工作流

```
流A(数据):  爬虫采集 → SimHash去重 → 清洗标准化 → 入库 → 图同步
流B(算法):  LLM抽取 → 技能归一化 → 演化分析 → 人岗匹配
流C(前端):  全景图谱 → 岗位详情 → 匹配诊断 → 演化看板
流D(QA):    Golden标注 → 基线评估 → LLM评估 → 质量门禁(F1≥90%)
```

**流程图示意**:

```
爬虫(拉勾/51Job/BOSS)
    │
    ▼
┌──────────┐    ┌──────────┐
│  去重     │    │  清洗     │  ← 并行执行(DAG)
└─────┬────┘    └─────┬────┘
      └──────┬────────┘
             ▼
       ┌──────────┐
       │  入库    │
       └────┬─────┘
            ▼
      ┌──────────┐
      │  图同步  │──→ Neo4j 知识图谱
      └──────────┘
            │
            ▼
    ┌───────────────┐
    │  LLM JD抽取   │──→ 归一化 → 抗幻觉验证 → 写入图谱
    └───────┬───────┘
            ▼
    ┌───────────────┐
    │  演化分析     │──→ 信任度 → 涌现检测 → 路径发现
    └───────┬───────┘
            ▼
    ┌───────────────┐
    │  人岗匹配     │──→ 差距分析 → 学习路径规划
    └───────────────┘
```

> **A讲**:
> 整个系统由四条并行工作流驱动。我用一个实际场景来解释数据如何流转：
>
> 第一步，爬虫从拉勾、51Job、BOSS直聘等平台采集JD。我们采用了**双模式采集策略**——对于简单的站点用HTTP请求直连，对于有反爬机制的站点则使用Playwright无头浏览器配合住宅代理。
>
> 第二步，原始数据经过DAG编排的流水线，**去重和清洗可以并行执行**，效率翻倍。SimHash算法用于快速检测内容重复。
>
> 第三步，LLM引擎从清洗后的JD中抽取结构化信息——不仅是技能名称，还包括技能级别、经验要求、学历要求、职责描述等。抽取结果经过**别名归一化和抗幻觉验证**后才写入Neo4j，确保图谱质量。
>
> 第四步，基于构建好的图谱，演化分析模块检测技能的涨跌趋势，匹配引擎完成人岗匹配并生成学习路径。

### 幻灯片 6 | 核心算法亮点(二) — LLM智能抽取

**标题**: 六步抽取管线 · 抗幻觉 · A/B测试

**抽取流程**:

```
JD文本 → PII脱敏 → Prompt填充 → LLM调用 → JSON解析
    → Pydantic验证 → 技能名清洗 → 别名归一化 → 向量归一化
    → 反幻觉验证 → 写入Neo4j
```

**关键技术指标**:

| 指标 | 数值 |
|------|------|
| 抽取F1 Score | 0.872 (接近90%目标) |
| 别名映射组数 | 100+ |
| 向量归一化阈值 | 0.85 |
| 最小来源数验证 | 3个独立来源 |
| 置信度门禁 | ≥0.80 |

> **A讲**:
> 信息抽取是整个系统的"感官"——它决定了上游图谱的质量。我们的抽取管线有六个关键步骤：
>
> **第一步，Prompt工程**。我们设计了结构化的System Prompt，引导LLM输出JSON格式的技能信息。这里有一个创新点——我们实现了**Prompt A/B测试框架**，可以同时运行新旧版本Prompt，通过实际F1指标决定哪个版本上线。
>
> **第二步，JSON解析与Pydantic验证**。LLM输出是文本，我们用三层解析策略——先尝试严格JSON解析，失败后用规则修复引号和逗号，再失败则用正则提取JSON块。解析后的数据通过Pydantic模型进行类型校验。
>
> **第三步，技能名清洗**。我们发现LLM经常输出带中文后缀的技能名，如"Python开发能力"、"Docker容器化技术"。我们设计了一个**递进式后缀剥离算法**，在保持语义完整的前提下，安全地剥离这些后缀。
>
> **第四步，别名归一化**。这是保证准确率的关键。我们维护了100+组别名映射，例如"node.js"→"Node.js"、"k8s"→"Kubernetes"。同时使用ChromaDB进行向量语义匹配，处理规则未覆盖的情况。
>
> **第五步，反幻觉验证**。LLM可能编造不存在的技能。我们通过**来源频次验证**（同一个技能在至少3个独立来源中出现才采信）和**语义对比**（与已有技能名称的相似度评估）来识别幻觉。
>
> **第六步，自动写入图谱**。抽取结果自动写入Neo4j，打通从数据采集到图谱构建的完整链路。

### 幻灯片 7 | 核心算法亮点(三) — 演化分析引擎

**标题**: 8步管线 · Z-score涌现检测 · 跨领域可迁移性

**流程图**:

```
Step 1: 加载快照
Step 2: 差异比对 (Diff)
Step 3: 信任度评分 (Trust)
Step 4: 抗幻觉检查 (Hallucination Guard)
Step 5: 涌现检测 (Emergence Finder)
         └─ Z-Score 算法
         └─ 跨领域可迁移性分析
Step 6: 路径发现 (Path Recommender)
Step 7: 保存变更日志 (Changelog)
Step 8: 更新图数据库 (EVOLVES_TO)
```

**涌现检测算法**:

```
z = (f(t) - μ) / σ

判定规则:
  z > 2.0 且 f(t)>3 且 sources≥3 → EMERGING (新兴)
  z > 1.5                          → RISING (上升)
  z < -1.5                         → DECLINING (下降)
  其他                             → STABLE (稳定)
```

> **B讲**:
> 演化分析是系统的"智慧大脑"，它能自动发现技能市场的动态变化。
>
> 这个8步管线涵盖了完整的分析流程。我重点介绍两个核心技术：
>
> **第一个是Z-score涌现检测算法**。我们采集每个技能在多个时间窗口内的出现频次，用历史数据计算均值和标准差，然后通过当前频次的Z-score来判断技能是否正在"涌现"。举个例子：如果"大模型"这个词在过去4周突然出现频率激增，Z-score达到3.0，系统就会标记为"新兴技能"并发出预警。
>
> **第二个是跨领域可迁移性分析**。我们发现有些技能(如Python、SQL)几乎出现在所有领域，而有些技能是领域专属的。我们计算每个技能的**可迁移性分数**(0到1)，综合考虑领域覆盖度、岗位多样性和分布均衡性。这对求职者的职业规划很有价值——如果你学会一个高可迁移性的技能，就等于获得了多个领域的入场券。

### 幻灯片 8 | 核心算法亮点(四) — 智能匹配引擎

**标题**: 4层回退 · 技能差距分析 · 学习路径规划

**匹配流程**:

```
求职者技能输入
    │
    ▼
岗位Profile加载 ── Tier 1: PositionRepository (缓存)
                 ── Tier 2: Neo4j 图查询
                 ── Tier 3: PostgreSQL
                 ── Tier 4: 硬编码回退
    │
    ▼
内容膨胀修正(CII) ── 防止"技能通胀"对评分的影响
    │
    ▼
技能匹配评分 ── 精确匹配 + 模糊匹配(SequenceMatcher)
             ── 熟练度覆盖度评估
    │
    ▼
技能差距分析 ── 已掌握 / 部分掌握 / 完全缺失
    │
    ▼
学习路径规划 ── 先修关系遍历 → 学习资源关联
```

**输出示例**:

```
匹配分数: 0.72
总体评价: 基础能力可支撑转岗，但仍需补齐关键缺口
缺失技能: Docker(先修:Linux), Kubernetes(先修:Docker)
预估学习时间: 4-6周（兼职学习）
推荐路径: Linux → Docker → Kubernetes → 微服务
```

> **A讲**:
> 匹配引擎是系统面向最终用户的核心功能。它的设计哲学是**"任何时候都能给出结果"**。
>
> 加载岗位Profile时，我们有四层回退机制：先从PositionRepository缓存加载，缓存未命中则查询Neo4j图数据库，图库不可用则查PostgreSQL，最后还有硬编码的Profile作为保底。这种策略确保了系统的高可用性。
>
> 匹配评分采用**混合策略**：精确匹配(别名归一化后直接比较) + 模糊匹配(SequenceMatcher字符串相似度) + 熟练度覆盖度。最终得分的计算公式为：`score = recall × (0.65 + 0.35 × proficiency_coverage)`。
>
> 我们还实现了一个创新机制——**内容膨胀修正(CII)**。我们注意到有些岗位JD列了10+个必备技能，但实际工作中很多只需要"了解"级别。如果岗位要求技能数超过基线(6个)的1.2倍，我们就自动将边缘技能降级为"加分项"，避免对求职者产生不合理的评分压力。
>
> 匹配完成后，系统还会基于技能的先修关系图，自动生成**学习路径**。比如缺失"Docker"技能，系统会追溯出先修知识"Linux"，形成一个有序的学习路线。

### 幻灯片 9 | 质量保障体系

**标题**: 评估驱动开发 · Golden Set · F1质量门禁

```

                                │
                                ▼
                          质量门禁
                     F1 ≥ 0.90 → PASS
                     F1 < 0.90 → FAIL
```

**当前指标**:

| 评估项 | 指标值 | 门禁值 | 状态 |
|--------|--------|--------|------|
| JD抽取F1 | 0.872 | 0.90 | 🟡 接近 |
| 单元测试覆盖 | 68.89% | 60% | ✅ 达标 |
| 后端测试数 | 184 passed | - | ✅ |
| 前端测试数 | 18 passed | - | ✅ |

> **B讲**:
> 我们的质量保障体系体现了**"评估驱动开发"**的理念。在项目启动之初，我们就投入大量精力构建了Golden Set——50条人工标注的JD，每条都标注了精准的技能列表作为"标准答案"。
>
> 在此基础上，我们建立了三阶段评估体系：
>
> **阶段一，基线评估**。用纯粹的规则和关键词匹配做抽取，得到一个F1基线(约0.65)。这告诉我们"不使用LLM能做到什么程度"。
>
> **阶段二，LLM模拟评估**。用不同参数(采样温度0.03/0.05/0.08)模拟LLM输出，测试系统在不同随机性下的稳定性。
>
> **阶段三，真实LLM评估**。用实际的生产管线(讯飞星火/DeepSeek)抽取50条JD，计算真实F1分数。目前已经达到0.872，距离90%的最终目标只有一步之遥。
>
> 每次代码变更后，CI流水线会自动运行这些评估，确保F1不会回退。这套体系让我们对系统的质量有**量化的、可追溯的信心**。

### Q1: 你们和市面上已有的招聘网站(如Boss直聘、猎聘)有什么区别？

> **A答**:
> 市面上的招聘平台本质是"信息撮合"，它们的关键能力是搜索和推荐算法。而星图的定位是**"能力知识基础设施"**。
>
> 具体来说有三个本质区别：
> 1. **数据价值维度不同**。招聘平台的数据是扁平的——一份简历、一个岗位。星图的数据是结构化的知识图谱——技能之间存在先修、包含、演进等多种关系，能回答"学Python后下一步该学什么？"这类问题。
> 2. **分析深度不同**。我们的演化分析能自动检测新兴技能，比如"大模型"相关技能在近期的爆发式增长。这是招聘平台不具备的行业洞察能力。
> 3. **开放性不同**。星图的API是开放的，可以集成到企业的HR系统、学校的课程体系、个人的学习计划中，而不仅仅是做一个招聘网站。
>
> 当然，我们未来也可以考虑与招聘平台合作——由星图提供能力评估和分析服务，由招聘平台提供岗位对接。

### Q2: 你们的抽取F1目前0.872，距离90%目标还有差距。瓶颈在哪里？怎么提升？

> **B答**:
> 这是一个非常好的问题。我们分析了当前低F1的样本，发现主要有三个瓶颈：
>
> **瓶颈1：中文技能名的边界模糊**。比如"数据分析"和"数据分析师"、"数据挖掘"和"数据挖掘算法"——LLM有时输出详细版本，Golden Set标注的是简洁版本，导致假阳性或假阴性。解决方案是优化归一化规则，增加更多上下文感知的匹配策略。
>
> **瓶颈2：部分技能归类错误**。LLM可能把加分项技能(Python基本能力)误归为必备项，或者反过来。我们在评估时是分别计算required和bonus的F1的，归类错误会拉低总分。解决方案是优化抽取Prompt，更明确地区分"必备"和"加分"。
>
> **瓶颈3：特定领域的专业术语差异**。在一些细分领域(如物联网嵌入式开发)，同一技能可能有多种叫法。我们的别名映射在通用IT领域覆盖较好，但在细分领域还有差距。解决方案是持续扩充别名库，特别是针对低F1样本的专项优化。
>
> 我们计划通过针对性的10样本优化和Prompt A/B测试，在下一次迭代中达到0.90的目标。

### Q3: 你们的涌现检测用Z-score，为什么不用更复杂的时序预测模型(如Prophet、LSTM)?

> **A答**:
> 选择Z-score而不是更复杂的模型，是基于三个考量：
>
> 1. **数据量限制**。我们的项目从启动到现在只有10周，积累的时序数据有限(每个技能只有4-6个时间窗口的数据点)。对于Prophet、LSTM这类数据饥渴模型，样本量远远不够。
>
> 2. **可解释性**。Z-score的计算过程完全透明——用户可以看到"这个技能被标记为新兴，因为当前频次比历史均值高出3个标准差"。这种可解释性在"预警"场景中非常重要，评委和用户都能理解。
>
> 3. **计算效率**。Z-score是O(n)的计算复杂度，可以在毫秒级完成对所有技能的分析。而深度学习模型需要GPU,部署和运维成本都更高。
>
> **但这不是终点**。随着数据积累(预计3-6个月后每个技能有20+个时间窗口)，我们计划引入更先进的时序模型。我们在架构上已经预留了这个扩展点——`EmergenceFinder.detect()`方法可以替换底层的统计算法，而上层的接口完全不变。

### Q5: 你们提到"契约优先"，这个具体怎么执行的？

> **A答**:
> 契约优先是我们团队最核心的开发纪律。具体执行分三步：
>
> **第一步，变更申请**。任何涉及API的变更，发起者先在starmap-contracts/目录下修改openapi.yaml文件。这是一个纯文本的YAML文件，用git diff可以清晰看到变更内容。
>
> **第二步，团队评审**。修改后的契约文件通过PR提交，至少需要技术负责人+相关模块负责人两人签字。这一步的核心是让所有相关方(特别是前端和后端)在"接口长什么样"上达成一致。

> **第三步，代码生成**。后端基于契约文件开发API实现，前端基于契约文件生成TypeScript类型定义(通过openapi-typescript工具)。这样前后端是"同源"的，从根上避免了联调冲突。
>
> 项目实施10周以来，我们几乎没有发生过因接口不匹配导致的联调问题。这就是契约优先的价值所在。

### Q6: 你们的系统如何保证实时性？

> **B答**:
> 我们设计了**三层实时性保障机制**：
>
> **第一层，数据流水线的SSE实时推送**。当流水线运行时，每个阶段的状态变化(如爬虫进度、去重结果、入库数量)都通过Server-Sent Events实时推送到前端监控页面。评委可以看到"正在爬取第3/50页..."这样的动态进度。
>
> **第二层，图谱查询的即时响应**。图谱数据存储在Neo4j中，查询是毫秒级的。前端的三层钻取(领域→岗位→技能)每次都是按需加载，而不是一次性拉取全部数据。
>
> **第三层，匹配引擎的在线计算**。人岗匹配是实时计算的，而不是预先算好的。这意味着用户只要上传简历、选择岗位，就能立即得到匹配结果和差距分析。匹配计算通常在1-2秒内完成。
>
> 对于异步耗时任务(如每周的演化分析)，我们使用Celery异步执行，完成后通过回调通知前端。这样既保证了用户体验的流畅性，又不阻塞核心业务流程。

### Q8: 你们的技术栈选型有什么特别的考量和权衡？

> **B答**:
> 有几个关键的权衡决策值得一提：
>
> **FastAPI vs Django**：我们选择FastAPI而不是Django，是因为(1)异步原生支持，对LLM调用的高并发场景更友好；(2)自动生成OpenAPI文档，天然支持契约优先；(3)轻量级，更贴合微服务架构。
>
> **Neo4j vs 纯关系型数据库**：技能图谱的核心是"关系"——技能之间的大量关联在关系型数据库中需要复杂的JOIN查询，而在Neo4j中只需要一个MATCH语句。经过基准测试，Neo4j在图遍历查询上比PostgreSQL快了20-50倍。
>
> **讯飞星火 vs GPT-4**：我们一开始就评估过GPT-4，其抽取质量确实更好，但API成本是星火的10倍以上，而且在国内部署存在合规问题。星火的中文理解能力在同类产品中是最好的，性价比最优。
>
> **小米MiMo v2.5**是近期才接入的，它是一个推理模型，在特定结构的输出上比通用模型更稳定。目前我们通过A/B测试来比较不同模型的表现。
>
> **Scrapy + Playwright**：Scrapy是经典的爬虫框架，效率高但容易被反爬。Playwright是浏览器自动化，能模拟真实用户行为，但速度慢一些。我们采用"HTTP优先，Playwright兜底"的双模式策略，兼顾效率和可用性。

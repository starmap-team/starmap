# 多端数据统一与防漂移架构方案

> **状态**: 设计提案（待评审）
> **日期**: 2026-08-13
> **来源**: deep-interview 4 轮访谈收敛（歧义度 14%）+ 代码事实核验
> **关联技术债**: C-1（PG↔Neo4j 双存储 SSOT 漂移，见 `.planning/STATE.md` §2）

---

## 0. 执行摘要

系统以 **PostgreSQL 为唯一事实源（SSOT）**、**Neo4j 为派生图谱投影**。当业务模块（抽取/审核/演化/流水线）产生新数据时，PG 先行写入、Neo4j 异步投影，两者之间必然存在**投影间隙**；加上历史遗留的孤儿节点与不一致的口径定义，admin「数据源诊断」报告当前显示 **岗位总数 10.1% critical（35 孤儿节点）、技能总数 10.8% critical（91 孤儿 Skill）**。

本方案确立三层目标架构：**写路径 PG 先行 → 修复引擎自动投影缺失 + 孤儿审批门控删除 → 分层口径观测与告警**，使双库达到"分层严格一致"（岗位/技能按 canonical_id 对齐全等、关系边按 REQUIRES 投影子集对齐、待审/已发布以 PG 状态为唯一源），并给出 P1–P4 分阶段实施计划、风险矩阵与可测试验收标准。

## 1. 现状诊断（2026-08-13 实测）

### 1.1 三源数据全景

| 指标 | API 返回 | PostgreSQL | Neo4j | 差异 | 状态 |
|------|---------|-----------|-------|------|------|
| 岗位总数 | 346 | 311 | 346 | 10.1% | ⚠ critical（35 孤儿节点）|
| 技能总数 | 843 | 752 | 843 | 10.8% | ⚠ critical（91 孤儿 Skill）|
| 关系边数 | 3433 | 3433 | 3433 | 0% | ✅ 一致（口径 = 全部边类型）|
| 待审核岗位 | 127 | 127 | 127 | 0% | ✅ 一致 |
| 已发布岗位 | 184 | 184 | 184 | 0% | ✅ 一致 |

同步健康卡（Phase 5 Step 4）：孤儿 Position **0** / 孤儿 Skill **0** / 同步健康度 ok / 最近 reconcile ok。

### 1.2 关键矛盾：健康卡与总数表两套判定口径

- **健康卡**按 `canonical_id` 集合差判定：`set(Neo4j.canonical_id) - set(PG.canonical_id)` → 0 孤儿 → "ok"
- **总数表**按**原始节点计数**判定：`count(:Position)=346` vs `count(position_records)=311` → 35 差额

两套口径对不上：35/91 个差额节点是 **canonical_id 缺失或指向不存在 PG 行的历史节点**，未被健康卡的 canonical_id 对齐识别为孤儿，却真实存在于图谱中污染总数。**判定标准不统一本身就是漂移的一种表现。**

### 1.3 写路径与现有修复手段

```
抽取/审核/演化/流水线
   │  ① 写 PG（position_records / skill_records / position_skill_relations）
   ▼
PG (SSOT)
   │  ② graph_sync 阶段（D8f 增量，since=run.started_at）投影 Neo4j
   │  ③ 审核即入图：approve → sync_approved_position_to_graph（D8f）
   ▼
Neo4j (派生投影)
```

- **修复手段（现状）**：手动 `POST /admin/reconcile-neo4j`（`GraphProjector.reconcile_all`：PG→Neo4j upsert + 孤儿剪枝，写 audit_events）+ cron `reconcile_graph_task`（每日 03:00）
- **无自动触发**：业务写入后不自动修复，依赖每日 cron 或人工
- **无审批门控**：`reconcile_all` 的孤儿剪枝直接删除，无预览/审批/审计闭环
- **删除不闭环**：PG 记录删除/审核拒绝时，Neo4j 节点无级联清理路径（D8g 已把 `removed` 变更纳入 write_back 删**关系**，但删**节点**路径仍缺）

## 2. 根因分析

| # | 根因 | 证据 | 影响 |
|---|------|------|------|
| R1 | **投影只增不删**：graph_sync 只 MERGE 补齐节点/边，不清理 PG 已不存在的节点 | `GraphProjector` upsert 为主，剪枝仅 reconcile 手动触发 | 孤儿节点长期累积 |
| R2 | **历史遗留无 canonical_id 节点**：canonical_id 对齐机制（D5）之前的节点、merge_duplicates 残留 | 346-311=35、843-752=91 | 总数口径永远对不上 |
| R3 | **判定口径不统一**：健康卡（canonical_id 差）与总数表（原始 count）两套标准 | admin_data_truth.py:218 vs :132 | 报告自相矛盾，误导运维 |
| R4 | **边数口径漂移**：`admin/stats` 报 582（PSR 记录数）vs data-truth 报 3433（全部边类型） | 报告说明文案自述 | 同一"关系边数"两个数字 |
| R5 | **修复无自动化**：依赖每日 cron + 手动触发，业务突发（流水线 run）后数小时才收敛 | celery_app.py:229 cron | 漂移窗口长 |

## 3. 目标架构（PG 权威 + 自动修复 + 审批门控）

```
业务模块（抽取/审核/演化/流水线）
   │  写 PG 先行（SSOT 唯一写入点）
   ▼
┌─────────────────────────────────────────────┐
│  PG: position_records / skill_records / PSR  │
└─────────────────────────────────────────────┘
   │  事件流：run 完成 / approve / reject / delete / 定时 tick
   ▼
┌─────────── 修复引擎 RepairEngine ───────────┐
│  ① 投影层 Projector（自动、幂等、无审批）       │
│     - 缺失节点/边 → MERGE 补齐（复用 GraphProjector）│
│     - 触发：事件驱动 + 定时兜底（节流防风暴）      │
│  ② 孤儿层 OrphanDetector（canonical_id 严格对齐）│
│     - 无 canonical_id / 指向不存在 PG 行 → 孤儿清单│
│     - 引用检查（被非孤儿节点引用 → 不列为可删）     │
│     - 可安全清理 → 写入 orphan_cleanup_queue（待审批）│
│  ③ 门控层 ApprovalGate（删除需审批）             │
│     - admin 数据源诊断 tab：孤儿清单预览 + 批准删除 │
│     - 批准后删除（级联边）+ audit_events 审计     │
│  ④ 口径层 MetricContract（分层严格一致）          │
│     - 边数口径：Neo4j REQUIRES 边 == PSR 行数    │
│     - 岗位/技能：canonical_id 对齐全等            │
│     - 待审/已发布：PG 状态唯一源                  │
└─────────────────────────────────────────────┘
   ▼
Neo4j（派生投影，与 PG 零漂移）
   ▼
观测：data-truth 报告（分层口径统一）+ 漂移告警（>1% warn / >10% critical）
```

### 3.1 分层严格一致口径（验收定义）

| 层 | 一致定义 | 实现方式 |
|----|---------|---------|
| 岗位/技能 | Neo4j 节点数 == PG 行数，且 canonical_id 双向对齐（0 孤儿、0 缺失投影） | 修复引擎投影 + 孤儿清理后归零 |
| 关系边 | Neo4j `(:Position)-[:REQUIRES]->(:Skill)` 边数 == `position_skill_relations` 行数 | 报告边数口径重定义（对齐 admin/stats 582 语义） |
| 待审核/已发布 | PG `review_status` 计数为唯一源；Neo4j 不存状态 | 审计链路正确即达标（现状已 0%） |

### 3.2 复用与新增

- **复用**：`GraphProjector.reconcile_all`（upsert+prune 已有）、`admin_data_truth.py` 报告框架、`audit_events` 表、admin 数据源诊断 tab
- **新增**：
  - `orphan_cleanup_queue` 表（或复用 audit 驱动队列）：孤儿清单 + 审批状态机（pending/approved/rejected/cleaned）
  - `RepairEngine` 服务（`app/services/repair_engine.py`）：投影触发 + 孤儿检测 + 审批执行，全部经 services 层（守 `test_layer_boundary`）
  - 事件钩子：流水线 run 完成、审核 approve/reject、岗位删除 → 触发投影（节流）
  - 口径层：data-truth 边数指标改为 REQUIRES 子集计数 + 前端说明文案更新（契约先行）

## 4. 分阶段实施计划

> 每阶段独立可验收，按序推进；阶段间可暂停评审。

### P1 — 修复引擎骨架 + 自动投影（消除"只增不删"入口）

- **做什么**：
  1. 新建 `app/services/repair_engine.py`：`RepairEngine.ensure_projection()`（幂等投影，复用 GraphProjector）+ `RepairEngine.detect_orphans()`（canonical_id 严格对齐，含无 canonical_id 节点）
  2. 事件钩子：流水线 run 完成后 + 审核 approve/reject 后自动触发 `ensure_projection`（节流：同一 run 只投影一次）
  3. 统一孤儿判定口径：健康卡与总数表共用 `detect_orphans()`（修 R3）
- **验收**：触发业务写入后，缺失节点 5 分钟内自动补齐；`data-truth` 健康卡与总数表口径一致（无自相矛盾）；pytest/vitest 绿
- **风险**：投影风暴 → 幂等 + 去重 + 节流（每 run 至多 1 次）

### P2 — 孤儿审批队列 + 删除门控（解决当前 35/91 孤儿）

- **做什么**：
  1. `orphan_cleanup_queue` 表（Alembic 迁移）：孤儿清单（type/name/canonical_id/reason/status/created_at）
  2. admin 数据源诊断 tab 增加「孤儿待清理」区：清单预览（含引用检查结果）+ 批准/拒绝按钮（沿 ContentReviewPanel 模式）
  3. 批准后删除：级联边 + 节点，写 `audit_events`（event=graph_orphan_cleanup）
  4. 引用检查：被非孤儿节点引用的孤儿不列入可删（防误删）
- **验收**：35 岗位 + 91 技能孤儿经审批后归零；`data-truth` 岗位/技能总数差异降为 0%；删除记录可审计；误删防护（引用检查）有单测
- **风险**：误删 → 审批门控 + 引用检查 + dry-run 预览

### P3 — 报告口径重构（修 R4 边数口径 + 前端契约）

- **做什么**：
  1. `admin_data_truth.py` 边数指标改为 Neo4j `REQUIRES` 子集计数（对齐 PSR 语义）
  2. 契约先行：`starmap-contracts/openapi.yaml` + `npm run gen:api` 同步；`DataTruthPanel.vue` 说明文案更新（区分"REQUIRES 边"与"全类型边"）
  3. 健康卡判定与总数表共用同一口径函数
- **验收**：报告中边数 = PSR 行数（口径一致）；前端渲染无 TS 错误；browser-use 验证 admin 数据源诊断无异常
- **风险**：口径变更影响既有解读 → 文案+工具提示说明迁移

### P4 — 观测/告警/回归测试

- **做什么**：
  1. 漂移告警：`data-truth` 定时扫描（如每 5 分钟）差异 > 阈值 → 告警日志/看板标记（沿 SSE 或轮询）
  2. 端到端回归测试：模拟业务写入（抽取/审核）→ 断言双库分层一致（`test_data_consistency_e2e.py`）
  3. CI 门禁：修复引擎单测（投影幂等/孤儿检测/审批状态机/引用检查）
- **验收**：模拟写入后双库零漂移断言通过；告警在阈值超限时触发；全量 pytest 绿
- **风险**：测试依赖真实 PG/Neo4j → 沿用 `db_session` fixture skip 模式

## 5. 风险矩阵与回滚

| 风险 | 概率 | 影响 | 缓解 | 回滚 |
|------|------|------|------|------|
| 误删有业务语义节点（canonical_id 对齐 bug） | 中 | 高 | 审批门控 + 引用检查 + dry-run 预览 | 清理前导出清单，支持 `restore` 脚本回灌 |
| 自动投影风暴（高频触发） | 中 | 中 | 幂等 MERGE + 节流（每 run 一次） | 关闭事件钩子开关，回退定时兜底 |
| 报告口径变更误导运维 | 低 | 中 | 契约先行 + 文案工具提示 | 保留旧口径字段（deprecated 标记） |
| 审批队列膨胀 | 低 | 低 | 队列去重 + 自动合并同 canonical_id | 直接清表（无业务影响） |
| 删除失败半途（Neo4j 部分删除） | 低 | 中 | 逐项事务 + 失败重试 + audit 记录 | 重新跑 detect_orphans 补清理 |

## 6. 验收标准（对应访谈确认的分层严格一致口径）

- [ ] **岗位/技能层**：`data-truth` 岗位总数/技能总数差异 = 0%（Neo4j 节点 == PG 行，canonical_id 双向对齐无孤儿）
- [ ] **关系边层**：报告中 Neo4j `REQUIRES` 边数 == `position_skill_relations` 行数（口径重构后）
- [ ] **状态层**：待审核/已发布以 PG `review_status` 为唯一源，三源一致（现状保持）
- [ ] **自动修复**：业务模块写入后，缺失节点/边自动投影（无审批）；孤儿删除经审批队列且记录审计
- [ ] **判定统一**：健康卡与总数表共用同一孤儿判定口径，不再自相矛盾
- [ ] **回归**：模拟业务写入 → 双库分层一致断言通过；全量 pytest 2270+ / vitest 420 不回归

## 7. 非目标（明确排除）

- 不做**写路径强一致双写**（PG+Neo4j 原子事务）——侵入全部写路径，风险收益比差（用户已确认选"PG 权威+自动修复"）
- 不做 Neo4j 存储 `review_status` 状态——状态仍以 PG 唯一（分层口径已确认）
- 不重构关系边数据模型（PG 侧补全边类型）——通过口径重定义解决语义差异

## 8. 根因查审结论（2026-08-13 深挖，含批量清理实证）

批量批准 63 个无引用孤儿后，技能差 10.7%→3.2%、岗位差 10.1%→9.9%；剩余 **59 个孤儿全部「缺唯一标识·被引用」**（34 岗位 + 25 技能），其引用边是 **PREREQUISITE（学习路径前置）与 RECOMMENDED_FOR**——来自其他技能/学习资源节点，**不是岗位 REQUIRES**。

### 根因链条 R1–R4

| # | 根因 | 证据 | 影响 |
|---|------|------|------|
| R1 | **历史 name-MERGE 不设 canonical_id**：`graph_writer.py` `MERGE (s:Skill {name})`/`MERGE (p:Position {name})`（D5 前及未传 canonical_id 的调用）创建无标识节点 | graph_writer.py:471/531 | 59 个无 canonical_id 节点 |
| R2 | **名称漂移阻断自动对齐**：D5 链接只做精确 name 匹配；LLM 抽取名（React.js）≠ PG 归一化名（React） | 实测: React.js↔React、CSS↔CSS3、REST↔REST API、Windows Server↔Windows Server (2022/2025)、SEO Manager↔SEO Specialist | 13 个同实体无法自动链接 |
| R3 | **PG 回填不覆盖历史技能**：graph_sync 的 `upsert_skill_record` 只回填**当次 run 抽取载荷**（since 过滤），历史 name-MERGE 节点永不回填 PG | stage3_services.py:432-466 | 46 个技能 PG 完全无记录（Network Administration、VMware、ERP、Neo4j、知识图谱…）|
| R4 | **这些"孤儿"不是垃圾**：被学习路径 PREREQUISITE/RECOMMENDED_FOR 引用，删除会破坏学习图 | 实测: VPN→Network Administration、Firewall→Network Administration 等 | 删除错误→需「链接 canonical_id」或「补录 PG」而非删除 |

### 关键结论

1. **无引用孤儿（63 个）= 真垃圾**（残留 name-MERGE 节点，无任何图关系）→ 批量删除正确，已完成。
2. **被引用孤儿（59 个）= 真实业务实体**：13 个同实体不同名（应**链接 canonical_id**，模糊匹配需人工确认防误链），46 个 PG 缺记录（应**补录 PG**——历史抽取未回填）。
3. **批量删除按钮对被引用项自动禁用是正确的安全设计**——本方案 P2.1 已把原因列语义化为「缺唯一标识·被引用」并在提示中说明。

### 遗留（P3/P4 建议）

- **P3a 链接建议**：detect_orphans 为被引用无标识节点计算 PG 模糊匹配建议（token 子集），UI 提供「确认链接」动作（SET canonical_id，非破坏、可逆）。
- **P3b 历史技能补录**：把 46 个无 PG 记录的技能从 Neo4j 回填 skill_records（一次性脚本，review_status 按引用来源判定）。
- **P4 写路径根治**：graph_writer 所有 MERGE 强制 canonical_id（无 id 不落图）；graph_sync 回填覆盖全部图谱技能而非仅当次 run。

*本附录基于 2026-08-13 批量清理实证 + Neo4j/PG 交叉查询（PREREQUISITE/RECOMMENDED_FOR 边分布、token 子集匹配量化）。*

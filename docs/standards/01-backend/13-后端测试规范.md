# 后端测试规范

## 1. 模块概述

本模块定义 StarMap 后端测试的规范和标准，涵盖单元测试、集成测试和测试基础设施。测试代码位于 `backend/tests/` 目录，共 76 个文件，约 18524 行代码。

**核心目标**：
- 确保后端代码质量，覆盖率 >= 60%
- 提供统一的测试基础设施（fixtures、helpers）
- 支持单元测试和集成测试
- 与 CI/CD 流程集成

**在系统中的位置**：位于 `backend/tests/`，被 `pytest` 执行，依赖 `backend/app/` 和 `backend/conftest.py`。

## 3. 架构设计

### 3.1 测试目录结构

```
tests/
├── __init__.py
├── conftest.py
├── unit/
│   ├── __init__.py
│   ├── test_*.py          ← 单元测试文件
│   └── ...
└── integration/
    ├── __init__.py
    └── test_*.py          ← 集成测试文件
```

### 3.2 测试金字塔

```
        ┌─────────┐
        │  E2E   │  ← Playwright (tests/e2e/)
        │ (少量) │
       ┌─────────┐
       │ 集成测试 │  ← pytest (tests/integration/)
       │ (中量) │
      ┌─────────┐
      │ 单元测试 │  ← pytest (tests/unit/)
      │ (大量) │
      └─────────┘
```

## 4. 接口规范

### 4.1 pytest Fixtures

```python
# conftest.py
import pytest

@pytest.fixture
async def client():
    """FastAPI 测试客户端。"""
    from app.main import app
    from httpx import AsyncClient
    async with AsyncClient(app=app, base_url="http://test") as client:
        yield client

@pytest.fixture
async def db_session():
    """数据库会话。"""
    from app.db.session import get_session_factory
    session = get_session_factory()()
    yield session
    await session.close()

@pytest.fixture
async def neo4j_driver():
    """Neo4j 驱动。"""
    from app.services.resources import resources
    yield resources.neo4j_driver
```

### 4.2 测试命令

```bash
# 运行所有测试
cd backend && poetry run pytest

# 运行单元测试

cd backend && poetry run pytest --cov=app --cov-report=html
```

### 5.1 测试命名规范

```python

def test_extract_from_jd_returns_skills():
    ...

def test_match_service_calculates_score_correctly():
    ...

def test_evolution_orchestrator_raises_on_invalid_input():
    ...
```

### 5.2 测试结构规范

```python
# Arrange - Act - Assert
def test_example():
    # Arrange
    input_data = {...}
    expected = {...}

    # Act
    result = function_under_test(input_data)

    # Assert
    assert result == expected
```

### 5.3 反模式

| 反模式 | 说明 | 正确做法 |
|--------|------|---------|
| 测试间有依赖 | 测试不稳定 | 每个测试独立 |
| 缺少断言 | 测试无效 | 明确断言预期结果 |
| 测试数据库 | 测试慢 | 使用内存数据库或 mock |
| 测试外部服务 | 测试不稳定 | 使用 mock |
| 测试私有方法 | 测试脆弱 | 测试公共接口 |

## 7. 变更管理

### 7.1 修改检查清单

修改测试模块时：

- [ ] 是否新增测试？是 → 确认覆盖所有分支
- [ ] 是否修改 fixtures？是 → 确认不影响其他测试
- [ ] 是否修改测试数据？是 → 确认数据有效性

### 7.2 契约影响

| 变更 | 影响 |
|------|------|
| 新增测试 | 提升覆盖率 |
| 修改 fixtures | 影响所有使用该 fixture 的测试 |
| 修改测试数据 | 影响测试结果 |

### 7.3 迁移要求

- 新增功能时必须同步新增测试
- 修改功能时必须同步更新测试
- 删除功能时必须同步删除测试
- 测试覆盖率必须 >= 60%

# 项目规范总纲

## 1. 模块概述

本文档为 StarMap 项目（人才能力星云导航系统）的强制性规范总纲，提取自 `AGENTS.md` 与 `CLAUDE.md`，适用于所有前后端开发者、AI Agent 与自动化流程。所有规范具有强制约束力，违反即视为技术债务。

**核心目标**：
- 建立跨团队一致的开发纪律
- 确保 API 契约优先、评估驱动、反幻觉三大原则落地
- 统一代码风格、Git 工作流与数据流认知

**在系统中的位置**：本文档是 `docs/standards/` 目录的入口文件，后续 15 份分模块规范均须引用并遵循本总纲。

│  ├─ evolution/    演化分析               │

### 3.2 数据流

```

简历   → match/diagnose → 技能对比 → 差距分析 → 学习路径
快照   → evolution/diff → 差异引擎 → 新兴技能 → 信任度聚合
```

## 4. 接口规范

### 4.1 契约优先原则

- **API 变更流程**：先改 `starmap-contracts/openapi.yaml` → 执行 `npm run gen:api` 同步前端 → 再改后端实现
- `starmap-contracts/` 是**跨团队真相源**，任何团队对 API 的疑问以该目录为准
- 违反契约优先视为 P0 级技术债务

### 4.2 API 字段命名

- 统一使用 `snake_case`（如 `match_score`, `skill_name`）
- 项目约定：前后端一致，**不做 camelCase 转换**
- 前端 TypeScript 类型定义中同样使用 snake_case 字段名

### 4.3 认证规范

- 生产环境 (`app_env=production`)：强制 JWT 验证
- 开发环境：Bearer token 或默认 dev 用户（宽松模式）
- Admin 端点额外叠加 `require_admin` 依赖
- 详见 `backend/app/dependencies.py` 规范文档

## 5. 编码规范（全局铁律）

### 5.1 Python 规范

| 项目 | 规范 |
|------|------|
| 文件/变量/函数 | `snake_case` |
| 类名 | `PascalCase` |
| 行宽 | 120 字符 |
| 格式化 | Ruff |
| 类型注解 | `from __future__ import annotations` + mypy |
| 文件命名 | 模块名简写（`graph.py`, `match.py`） |

### 5.2 前端规范

| 项目 | 规范 |
|------|------|
| 组件/Vue 文件 | `PascalCase` |
| 变量/函数 | `camelCase` |
| 类型检查 | `vue-tsc --noEmit` |
| 代码检查 | ESLint |

### 5.3 Git 约定

- **分支命名**：`fix/*`, `feat/*`, `chore/*`, `docs/*`
- **Commit 格式**：`type(scope): description (#PR)`
- **合并方式**：squash merge

### 5.4 反模式清单（禁止项）

| 编号 | 反模式 | 后果 | 检测方式 |
|------|--------|------|---------|
| A-01 | 直接修改 API 不改 `openapi.yaml` | 前后端契约断裂 | PR Review |
| A-02 | 生产环境暴露 Swagger/ReDoc | 信息泄露 | `main.py` 环境判断 |
| A-03 | 模型变更不走 Alembic 迁移 | 数据库不一致 | CI 检查 |
| A-04 | 技能抽取不附带信任度评分 | 反幻觉失效 | 单元测试 |
| A-05 | 在 `services/` 外直接写 Neo4j 查询 | 图/业务耦合 | Code Review |
| A-06 | 多处重复 simhash 实现 | 维护困难 | 静态扫描 |
| A-07 | 使用默认占位密码 `CHANGE_ME_IN_ENV` 上生产 | 安全漏洞 | `config.py` 启动校验 |

## 6. 测试规范

### 6.1 覆盖率要求

- **后端**：`pytest` 单元 + 集成测试，覆盖率 **>= 60%**
- **前端**：`vitest` 单元测试
- **E2E**：`Playwright` 冒烟测试

### 6.2 评估驱动

- 提交前必须确保 baseline 评测不降级
- `evaluation/` 目录包含 baseline、模拟 LLM、真实 LLM 三套评估套件
- 评估结果作为 PR 合并的必要条件

### 6.3 测试命令

```bash
# 后端
cd backend && poetry run pytest                    # 单元 + 集成 (覆盖率 >= 60%)

# 前端
cd frontend && npm run test                        # vitest

# E2E
python tests/e2e/smoke_test.py --base-url http://localhost:8000 --all
```

## 7. 变更管理

### 7.1 修改检查清单

修改任何模块前，必须确认：

- [ ] 是否涉及 API 变更？是 → 先改 `starmap-contracts/openapi.yaml`
- [ ] 是否涉及数据库模型？是 → 生成 Alembic 迁移
- [ ] 是否影响评估 baseline？是 → 运行评估套件确认不降级
- [ ] 是否新增外部依赖？是 → 更新 `pyproject.toml` / `package.json`
- [ ] 是否修改安全相关代码？是 → 额外安全 Review
- [ ] 是否修改配置项？是 → 更新 `.env.example`

### 7.2 契约影响评估

| 变更类型 | 影响范围 | 必须操作 |
|---------|---------|---------|
| API 路径/方法变更 | 前后端 + 契约 | 更新 openapi.yaml → gen:api → 通知前端 |
| 响应字段增删 | 前后端 + 契约 | 更新 openapi.yaml → 更新 Pydantic Schema |
| 数据库字段变更 | 后端 + 迁移 | Alembic migration → 更新 ORM Model |
| 核心算法变更 | 评估套件 | 运行 evaluation/ baseline |
| 配置项变更 | 部署脚本 | 更新 .env.example + docker-compose |

### 7.3 迁移要求

- **数据库迁移优先**：任何模型变更必须走 Alembic 迁移，禁止直接修改生产数据库
- **旧版兼容**：`app/pipeline/`（旧版 468 行）与 `app/core/pipeline/`（新版 2950 行）并存期间，旧版代码禁止新增功能，仅允许 bug 修复
- **空目录清理**：`core/graph_engine/`, `core/hallucination/`, `core/trust/` 已迁移到 `evolution/`，保留 `.gitkeep` 仅作占位，禁止恢复旧逻辑

# 架构设计规范

完整视图见 [系统架构](../../architecture/overview.md) 和 [数据存储](../../architecture/data-storage.md)。

## 后端边界

- `api/v1/`：HTTP 边界，不承载领域计算和持久化编排。
- `schemas/`：API Pydantic 模型唯一位置。
- `services/`：业务编排、PG/Neo4j 访问、图投影和外部适配。
- `core/`：领域算法与状态机。
- `models/`：ORM；不承载 API Schema。
- `tasks/`：薄 Celery 入口，调用 services/core。

依赖方向原则上是 API -> services -> core/models/infrastructure。允许 core 内部领域编排使用 models，但禁止 core 反向依赖 API。

## 数据边界

- PG 保存业务事实，写入成功后投影 Neo4j。
- Neo4j 使用 `canonical_id` 对齐 PG UUID。
- Redis 不是永久事实源。
- 同一列表 API 不混合 PG 与 Neo4j 后靠名称去重。

## 前端边界

Page -> composable/store -> API client。组件负责展示和局部交互；Store 负责共享状态；OpenAPI 类型和 JSON Schema 负责边界一致性。

## 评审问题

- 新逻辑是否放在唯一责任模块？
- 是否创建了第二个事实源或重复规则？
- 失败、重试、幂等和审计路径是否明确？
- API/数据库变化是否同步契约和迁移？
- 是否能用现有质量命令验证？
